test: make the browser-unreachable API surface explicit

Two independent things must line up for a UI feature to work: the Node API
serves the path, and src/lib/property-api.ts API_PATH allows it through the
browser proxy. A route satisfying only the first is invisible to the product -
every client fetch returns 404 "Unknown API route" before reaching the server.
A route satisfying only the second looks wired until a caller discovers the
missing implementation.

Three routes are currently in the first bucket. Each has a real route module
and passing tests, which is exactly what makes them misleading - someone
reading the repo reasonably assumes a tested, working endpoint is live:

  /api/coverage              server.js:185
  /api/price-drops           server.js:212 + routes/price-drop.js
  /api/portfolio/dashboard   server.js:206 + routes/portfolio-dashboard.js

Verified: none appears in API_PATH and none is referenced anywhere in src/.

They are deliberately NOT removed here. A CLI or external consumer may use
them, and deleting working code is not this test's call. What was missing was
any record that the state is intentional, so the test pins it:

  - known-reachable routes must still match API_PATH, so a shipped feature
    cannot quietly go dark
  - known-unreachable routes must not match, so one that gains a UI caller
    moves lists in the same commit
  - the count is pinned so the set cannot silently grow
  - each must still exist in server.js, so stale entries get removed

Validated by deleting "auction-calendar" from the allowlist: the guard failed
naming that route with "a shipped feature has gone dark behind a 404 the user
cannot diagnose" - the same failure mode as the saved-searches/:id/run bug
fixed in 9bbe7e8, which is the point of having it.
