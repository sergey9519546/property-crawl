test: pin the listing-id alias as a documented dead path

Finishing the audit of the a58f76f merge. The data layer, migrations,
schema copies, rent-roll period math, and the workspace/API proxy layers all
checked out sound. One item did not.

server/db/client.js documents:

  A canonical STATE-COUNTY-NUMBER id (e.g. "OH-CUY-10231") is an unambiguous
  alias for the source-namespaced record "SHERIFF-OH-CUY-10231".

NAMESPACED_ID is /^[A-Z]{2,3}-[A-Z]{2,3}-\d{2,6}$/, which is correct for the
documented input — but real listing ids are source-prefixed with prefixes of 4+
characters (USDA-MS-6274, TRSY-27-66-804, SHERIFF-...), and the first segment
allows only 2-3. Measured against data.js the alias matches 0 of 2094 ids.

The alias is inert, not broken: nothing in the app passes a STATE-COUNTY-NUMBER
form, so no lookup is mishandled. The hazard is that it reads as working.

Not widened on purpose. The "never a partial or numeric fragment" guarantee is
what stops getListingById('1') from matching a listing ending in "-1"; loosening
the pattern would trade a real safety property for nothing. Instead the
behaviour is pinned:

- the documented canonical form matches
- partial and numeric fragments do not
- the pattern matches none of the real ids
- the cause (4+ char source prefixes) is asserted explicitly
- exact lookup still resolves
- a numeric fragment still returns null, end to end

If the alias is ever needed, the test fails and directs the change to be made
deliberately rather than discovered as a silent null. The client comment now
carries the same warning, so the next reader is not misled at the source.
