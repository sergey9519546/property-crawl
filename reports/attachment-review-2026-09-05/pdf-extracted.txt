1. Executive Summary
This  report  documents  a  complete,  evidence-driven  reverse-engineering  analysis  of  
ServiceLink Auction (www.servicelinkauction.com) , the real-estate auction marketplace  
operated by ServiceLink, an FNF (Fidelity National Financial) company, and built on the Exos 
Technology auction platform. The investigation was performed exclusively against publicly 
accessible resources: static HTML, the deployed JavaScript application bundle, public API  
endpoints that respond to anonymous requests, and the site's declared sitemap files. No  
authentication was bypassed, no protected endpoint was accessed, and all probing was  
performed at a polite, rate-limited pace in accordance with the site's fully permissive  
robots.txt policy.
The analysis reveals a modern, well-architected platform: an Angular 21.2.17 single-page 
application (internal product name Exos.AuctionSpa, build 2026.07.31.0956) served as a 
static website from Azure Blob Storage, fronted by a Prerender.io middleware that supplies 
fully rendered HTML to search-engine crawlers. Application data flows through a REST  
microservice  layer  of  thirteen  ASP.NET  Core  services  exposed  at  
https://ui.exostechnology.com/api/*/v1/ and  a  mirror  gateway  at  
https://www.servicelinkauction.com/api/*/v1/,  with  a  fourteenth  SignalR  
service providing real-time auction push messaging. Salesforce operates as the system of  
record: listing identifiers carry Salesforce record-ID prefixes and custom detail fields retain 
the platform's __c suffix convention.
Key quantitative findings include a live public catalog of 5,900 searchable listings, a sitemap 
index of 16,358 property URLs, 26 active auction events, 52 state licensing disclosures, and 
a fully anonymous-accessible property data model covering pricing terms, bid increments,  
auction windows, photographs, and downloadable property reports. The report maps the  
complete anonymous-versus-authenticated API boundary, decodes the real-time bidding  
protocol, reconstructs the auction lifecycle state machine, and catalogs more than 240  
business-logic  constants  extracted  from  the  application  bundle.  All  evidence  files  
referenced throughout are preserved in the analysis workspace for verification.

4. Delivery Platform and Frontend Architecture
4.1 Hosting and Edge Delivery
The production frontend is hosted as an  Azure Blob Storage static website . Response  
headers from every static asset carry the unambiguous Blob service fingerprint:  x-ms-
version: 2009-09-19, x-ms-blob-type: BlockBlob, x-ms-request-id, and Azure-
formatted ETags (0x8DEF4277D18039B). Static content is served over HTTP/2 with a one-
year  strict-transport-security policy. Property photography and PDF reports are  
stored  in  dedicated  blob  containers  under  the  /auction-photos/ and  /auction-
documents/ virtual paths; images carry custom blob metadata (x-ms-meta-name, x-ms-
meta-mime, x-ms-meta-created, and a GUID-valued x-ms-meta-version), indicating 
an automated ingestion pipeline. Source maps are correctly stripped from production (all  
.js.map requests return 404), which is the right hardening posture for a production  
bundle.
4.2 The Application Shell and Build Pipeline
Normal visitors receive a 1,053-byte shell document. Its metadata declares the application 
identity:  <meta  name="application-name"  content="Exos.AuctionSpa" with  
data-buildnumber="2026.07.31.0956" and  data-deploytime="2026-08-
07T01:57:49Z". The shell bootstraps a standard Angular CLI webpack production build  
(runtime / polyfills / scripts / main  hashed chunks; global webpack chunk  
registry webpackChunkAuctionSpa; Trusted Types policy  angular#bundler). Notably, 
all lazily-loaded feature modules are inlined into the single 5.49 MB main bundle rather  
than emitted as separate chunk files, which is why the runtime chunk-name function exists 
but no on-demand chunks are fetched at runtime. The Google Maps JavaScript API is loaded 
synchronously in the shell with the places library. One build-pipeline defect was observed: 
the CSP nonce placeholder token CSP_NONCE is emitted literally into the shell rather than  
being  replaced  per-response,  so  the  GTM  script  tag  carries  a  literal  nonce  value  of  
"CSP_NONCE".

7.3 Search Filter DSL
Search requests are flat key-value query strings built by flattenObjectToQueryString 
and  mirrored  into  the  browser  URL  for  shareable  search  states.  The  complete  filter  
vocabulary was extracted from the criteria model and the constants registry: location  
(state, city, county, postalCode), property facts (propertyType, beds, baths, 
yearBuilt, InteriorSquareFeetMin/Max, LotSizeMin/Max, occupancyStatus), 
program (auctionProgram, listingProgramWebsite, showOnly, auctionPeriod, 
bidType),  auction  timing  ( AuctionStartDate, AuctionEndDate ),  direct  lookups  
(websiteUrl, globalPropertyId, auctionId, auctionNumber ),  special  modes  
(fdicAuctionsSearch=true for  FDIC-disposition  inventory  and  an  auction-calendar  
mode  keyed  by  auctionNumber),  and  pagination  ( limit, pageNum, pageSize,  
ContinuationToken). Sorts are driven by precomputed composite keys returned with  
each record: endingSoonest / endingLatest / recentlyListed  (with dashboard  
variants), each encoded as a rank-prefixed string such as "1_2026-09-16 11:00:00_3" - 
a faceted sort-key pattern typical of Azure search/cosmos indexing.
Every search result embeds currentDTTM (server clock) alongside the data, letting the SPA 
recompute countdown offsets on each page render without an extra round-trip to CurrentDTTM.
8. Listing Data Model and Business Taxonomy
8.1 Record Schema
Each  listing  record  spans  roughly  fifty  top-level  fields  organized  into  nested  groups.  
propertyInfo carries the physical asset (address, coordinates, beds/baths, interior and  
lot square footage, year built, occupancy, asset number, and both current and legacy  
website URLs).  auctionRunInfo carries the commercial  envelope: the auction event  
identity  (Salesforce  auctionId,  the  operational  awxId and  human  auctionNumber),  
program and method, start/end windows, starting bid, earnest-money percentage and  
minimum,  buyer's  premium,  co-op  commission,  and  long-text  transaction  terms.  
customDetail is  the  raw  Salesforce  custom-field  projection  -  bid  increment  tiers  
(increment_1__c through  increment_3__c),  funds  type  and  percentage,  proxy-bid  
toggle, and bid-count - which proves the system of record. listingStatus is a server-
computed  lifecycle  snapshot  (detailed  in  9.2).  Media  arrays  ( images,  documents) 
reference the public blob containers.

8.2 Program Taxonomy
The slug suffix visible in every property URL encodes the sales program. The mapping,  
reconstructed from constants, search results, and the help center, is:  trd = Traditional  
bank-owned REO online auctions (website label "Bank-Owned", with BULK and Total Debt  
sub-modes); cwt = CWCOT (HUD Claim Without Concession on Title, website label "Newly  
Foreclosed"); tps = Third-Party Sale foreclosure auctions (website label "Foreclosure Sale"), 
conducted on-site at courthouses with live simulcast; plus Short Sale and buyer-exclusive 
programs.  Each  program  carries  its  own  license  blocks,  buyer-premium  rules,  and  
inspection-access policies, all of which flow through the same record schema.
8.3 Salesforce as System of Record
Three independent fingerprints converge on Salesforce. First, identifier formats: listing IDs 
such  as  a1cDo0000011DTCIA2 and  property  IDs  such  as  a1lVO000004YfI5YAK are  
Salesforce record IDs (the a1c/a1l prefixes denote custom objects; the VO/Do segments  
encode pod and org). Second, the customDetail group retains raw API names with the __c 
custom-field suffix and a systemModStamp field. Third, dedicated services sync Salesforce 
data  changes  ( salesforcedatasyncsvc)  and  export  syndication  feeds  
(salesforcezillowexportsvc). The microservice layer therefore operates as a search-
and-transaction  mid-tier  over  Salesforce,  while  the  public  search  index  serves  
denormalized  snapshots  (each  record  includes  lastUpdated and  timestamp fields  
evidencing scheduled refresh, with listing snapshots flagged via listingSnapshot).

9.3 Bid Pricing Rules
Bid increments are per-listing and tiered: the quick-increment UI offers +$100, +$500, and +
$1,000 buttons sourced from  increment_1__c/2/3 (the values observed on both the  
target property and sampled listings). Proxy (maximum) bidding is supported: bidders  
submit a ceiling and the system bids on their behalf only when outbid, notifying them by  
email when the ceiling is reached; a proxy ceiling cannot be lowered (server rejection code 
CANTLOWERPROXYBID), and low bids are rejected with BIDAMOUNTTOOLOW. Sellers reserve 
the right to bid up to the reserve price themselves (disclosed in transaction terms), and  
reserve-met state is displayed on the PDP. The MAB (Minimum Acceptable Bid) windows -  
slaMABStartDateTime through  slaMABEndDateTime - gate the Quick Bid feature on  
qualifying listings.

13. Security Posture Observations
The  public  surface  is  well-disciplined.  Authentication  is  consistently  enforced  on  the  
account-scoped API plane (clean 401 envelopes with tracking IDs); no protected data was  
observed leaking through the anonymous endpoints - the anonymous data is the marketing 
catalog itself, including bid counts and current-bid polling, which the platform deliberately 
publicizes to drive auction participation. Client-embedded credentials are all public-by-
design browser keys (Google Maps, GTM, App Insights instrumentation key), which cannot 
authenticate anything. Transport security is strict: HSTS with includeSubDomains on the API 
hosts, Trusted Types on the SPA, and OAuth-style bearer handling with refresh machinery  
and telemetry masking of credential-shaped strings.
Two observations merit engineering follow-up (both are hygiene, not vulnerabilities). First, 
the CSP nonce pipeline defect: the shell emits the literal placeholder CSP_NONCE as both 
the script nonce attribute and the global value, indicating the deploy step that should mint 
a per-response nonce is not active on the static host - a consequence of static blob hosting 
that a small edge function could remedy. Second, the SPA fallback returns HTTP 200 for  
every  arbitrary  path  (including  the  removed  Meta  verification  file),  delegating  404  
semantics entirely to the client router; combined with prerender caching, stale URLs can  
linger in indexes. The Prerender.io tier itself enforces only a 100-request budget, which is a 
crawler-fairness limit rather than an application control.
All probing in this engagement stayed within anonymous GET semantics. No authentication, rate 
limit, or access control was circumvented, and no user account data was requested or collected.
